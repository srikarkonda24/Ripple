# Ripple — Project Memory

This file is the persistent record of what Ripple is, what's been built, what's been tried and rejected, and why. Read this at the start of any new session before continuing work — it exists so we don't re-derive or re-debate things that have already been settled.

## What Ripple currently is

Ripple is a **persistent project memory tool**. It keeps a living record of one software project — current architecture, key decisions and why they were made, approaches tried and rejected, and open questions — so that AI coding tools (Claude Code, Cursor, Codex) and the developer can pick up full context every session instead of starting from zero.

It is **not** a visualization product, not an "AI governance layer" for enterprise teams, and not a cross-tool (Slack/Notion/GitHub) organizational memory system. Those were all considered and explicitly set aside (see "Tried and rejected" below).

The underlying technical foundation — a real, deterministic code-structure parser plus an MCP server — still exists and works, and is being repurposed to serve project memory rather than (or in addition to) codebase concept maps.

## What's actually built and working

- **`ripple-parser`** — a Node/TypeScript script using `ts-morph` that walks a TypeScript/JavaScript codebase, finds every function/component, and traces function-call and JSX-usage relationships. Outputs `output.json` (nodes = functions/files, edges = call/usage relationships). Tested and working on AgentGuard's codebase (44 nodes, 54 edges).

- **`concepts.json`** — a hand-written (not automated) grouping of AgentGuard's `output.json` into 6 named concepts (Marketing Site, Diff Processing, Secret Scanner, Scan Orchestrator, GitHub Integration, Webhook Entry Point), each with a plain-English description and list of member functions/files. This was generated by an LLM (manually, in chat) reading the raw graph — **there is no automated pipeline for this yet**.

- **`ripple-mcp`** — a working MCP server (Node/TypeScript, `@modelcontextprotocol/sdk`, stdio transport) that loads `output.json` and `concepts.json` at startup and exposes two tools:
  - `list_concepts` — returns all concepts with name + description
  - `get_concept_context` — case-insensitive search over concept names/descriptions, returns matching concepts with their description and member file paths
  
  **Confirmed working end-to-end**: connected to Cursor via `.cursor/mcp.json` at the workspace root, Cursor successfully called both tools and used the returned data to answer a question accurately (e.g., "what handles GitHub integration" → correct concepts + file paths).

  **Known issue**: `ripple-mcp/data/` currently contains AgentGuard's `output.json`/`concepts.json`, not Ripple's own code. So queries return AgentGuard's structure even when working in the `Ripple` workspace. Not yet fixed.

- **`ripple-landing`** (or wherever the landing page currently lives) — a landing page that has been through several rewrites (see below). Most recent version reflects the "project memory" framing: hero "Your AI forgets everything between sessions. Ripple doesn't", a "From Project Memory" demo card, Decision Memory / No Re-explaining / Tried & Rejected / Agent Context via MCP feature cards, and an updated comparison table. A session-memory diagram (sessions connected to a shared memory layer) was designed to add to the Problem section but not yet confirmed as implemented.

## Key decisions and why

- **Concept-level grouping > function-level call graphs.** Tested both. A raw function call graph (e.g., "scanLine calls adjustSeverity") didn't feel useful or illuminating. Grouping into named concepts with plain-English descriptions ("Secret Scanner — scans code lines for exposed API keys") felt meaningfully better — this is the first thing in the whole project that produced a genuine "oh, that's what this is" reaction.

- **MCP server, no separate UI/dashboard.** Explicitly chosen over a CodeViz-style visual dashboard. Reasoning: a separate app to "check" alongside an AI chat is friction nobody wants; an MCP server that Cursor/Claude can call automatically, invisibly, mid-conversation is the right shape. Confirmed working in practice.

- **One project at a time, not an org-wide memory system.** Explicitly scoped down from "memory layer across GitHub/Slack/Notion/everything." Reasoning: that's a much bigger, multi-integration build with no validated foundation yet, and "connects everything" is itself "another thing to set up" — it doesn't solve the "don't make me check another app" concern, it makes it worse.

- **Local-first / runs on your machine** is a real, validated differentiator (from reading CodeViz's HN launch thread — many developers explicitly want code to never leave their machine, and CodeViz still hasn't fully solved this). `ripple-mcp` running locally and reading local files is inherently aligned with this, without extra work.

## Tried and rejected (don't re-propose these without new evidence)

1. **"Living codebase brain" / real-time knowledge graph for AI agents** (the original pitch, multiple times, reworded). Repeatedly re-surfaced via pasted documents ("Repository Intelligence Platform," "System Memory," "Architecture Copilot," etc.) — all variations of the same big-vision pitch. Each one felt compelling on paper but none were tested; this pattern (read a bigger-vision document → feel validated → don't test) repeated at least 5 times in this project's history. Treat new documents making this pitch as **not new information** — the idea has already been considered.

2. **Visualization as the core product** (function-level call graph, then concept-level map, then "better visualization than CodeViz"). Built and tested a working concept-map visualization on AgentGuard's own codebase. Reaction: "didn't find it that useful... maybe because it's just frontend stuff." Concluded that even concept-level visualization wasn't the core value — the value was in the *MCP-queryable data*, not in looking at a graph.

3. **Token-efficiency as the headline pitch.** Considered, researched (token costs are a real, measurable, discussed topic in the Cursor/Claude Code community as of 2026). Concluded it's a real *mechanism* but a weak *headline* — invisible to users, hard to demonstrate, and modern agentic tools already do reasonable codebase exploration on their own. Better as a supporting technical detail than the lead.

4. **Enterprise / "AI governance layer" framing** ("blast radius," "policy enforcement for AI-generated changes," compliance audit trails). Concluded this requires enterprise sales motion, security review, and trust-building that a solo student cannot realistically execute in the relevant timeframe. Pain may be real but the buyer is unreachable right now.

5. **Full-stack visualization** (connecting to AWS/Firebase/Supabase to show infrastructure, not just code). Rejected as a "foundation" — it's a large, separate, credential-sensitive integration effort bolted onto an already-unvalidated core. Could be a much later extension if the core proves out.

6. **CodeViz-style "better diagrams" as the wedge.** Researched CodeViz directly (YC S24 launch, HN thread). Concluded diagrams are CodeViz's whole product and a hard fight against a funded, year-ahead team — not a winnable or differentiated wedge for Ripple.

## Open questions (unresolved, worth testing)

- **Does the "project memory" idea actually help, in practice?** This is the most-grounded idea so far (motivated by this conversation's own dysfunction — repeatedly re-deriving the same ideas without persistent context) but it has not been tested at all yet, including on yourself. This file (`RIPPLE_MEMORY.md`) is itself the first test: does starting a session with this file produce a better conversation than starting cold?

- **At what codebase size/complexity does a pre-built concept map outperform "just ask Claude/Cursor to read the files directly"?** Still untested — everything so far has been on AgentGuard (44 functions), which is small enough that Claude/Cursor can plausibly just read it directly. Testing on a larger/unfamiliar codebase was proposed multiple times but never done.

- **How would concept-labeling be automated?** Currently requires manually pasting `output.json` into an AI chat and hand-writing `concepts.json` from the response. For this to work on arbitrary codebases, either `ripple-parser` or `ripple-mcp` needs to make a real LLM API call (with a user-provided key) and parse the response programmatically. Not yet built.

- **Would a `get_project_memory` MCP tool** (serving this memory file's contents, or a structured version of it, to Cursor/Claude automatically) be a natural third tool for `ripple-mcp` — connecting the "memory file" idea and the "MCP server" idea into one thing? Not yet explored.

- **Is this a startup, or a personal tool?** Repeatedly deferred. The honest position: prove it helps *you* first (via this file and the MCP server), then ask whether other developers have the same pain badly enough to want it as a product. No real user research has been done yet — this remains the single biggest gap across every direction explored.
